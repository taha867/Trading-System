# Item Model Compatibility — Backend

## Context

Second-to-last of the three problems reported against production (`CATALOG_FIXES_PLAN.md`; the item-picker search fix is Phase 1, already shipped — see `catalog-fixes-*-plan.md`). The user's need: a screen protector Item created under one Model (e.g. "iPhone XS") also fits other Models (e.g. "iPhone 11 Pro"), and they want to tag those additional Models on the Item so it's discoverable/visible for both.

Before this, `Item.model_id` was a single FK and the whole `catalog` domain (`Category`/`Brand`/`Model`/`Item`) was 100% generic CRUD via `build_crud_router()` (`backend/src/crud.py`) — no hand-written service existed, and there was no many-to-many relationship anywhere in the codebase. This is the first one. **Status: complete and verified**, including a real bug caught during implementation (see below) that the design/review passes did not predict.

## Change made

**New join table**, `backend/src/catalog/models.py`:
```python
class ItemCompatibleModel(Base):
    __tablename__ = "item_compatible_model"
    item_id: Mapped[int] = mapped_column(ForeignKey("item.id"), primary_key=True)
    model_id: Mapped[int] = mapped_column(ForeignKey("model.id"), primary_key=True, index=True)
```
`Item` gained the codebase's first `secondary=` relationship: `compatible_models: Mapped[list["Model"]] = relationship(secondary=ItemCompatibleModel.__table__, lazy="raise")` — one-directional, no `Model.compatible_items` back_populates (nothing needs that direction).

**Migration**: `backend/migrations/versions/2026-08-16_add_item_compatible_model.py` — autogenerated (`down_revision = 'a307efeb3de2'`, confirmed head via `alembic current` before running), reviewed, renamed from the autogenerated hash filename to the date-prefixed convention, then applied via `alembic upgrade head`. First composite-primary-key table in the repo (`PrimaryKeyConstraint('item_id', 'model_id', ...)`), matching the design exactly — autogenerate only detected the new table and its `model_id` index, nothing else. `backend/migrations/env.py`'s catalog import line updated to include `ItemCompatibleModel`.

**`backend/src/catalog/exceptions.py` (new)**: `ItemNotFound(NotFoundException)`.

**`backend/src/catalog/schemas.py`**: `Category`/`Brand`/`Model` schemas untouched. `Item` schemas became hand-written (matching every other hand-written-service entity — `ItemRead` no longer inherits `ItemCreate`):
- `ItemCreate`/`ItemUpdate` gained `compatible_model_ids: list[int]` (default `[]` on Create, `None` on Update — `None`/omitted means "leave untouched", confirmed by test).
- `ItemRead` gained `compatible_models: list[ModelRead] = []` (full nested reads, populated via `from_attributes`) plus a `@computed_field compatible_model_ids` deriving the flat id list from it — the established relationship-as-flat-list pattern already used in `purchasing/schemas.py`/`sales/schemas.py`.

**`backend/src/catalog/service.py` (new)** — full hand-written CRUD for Item:
- `create_item`/`update_item` explicitly validate `category_id`/`model_id`/each `compatible_model_id` exist and are active (adopting the same explicit-validation pattern every other hand-written service uses, rather than the generic factory's old "let Postgres's IntegrityError catch it" behavior). `Model` instances are assigned directly to `item.compatible_models` — `secondary=` means no manual `ItemCompatibleModel` row construction.
- `update_item` only touches `compatible_models` when `"compatible_model_ids" in payload.model_fields_set` — distinguishing "field omitted" from "explicitly cleared to `[]`". Requires `item` to arrive with `compatible_models` already eager-loaded (satisfied since `valid_item` always eager-loads it) so SQLAlchemy can diff against the loaded collection instead of needing a lazy load, which `lazy="raise"` forbids.
- `list_items` reproduces `category_id`/`sku`/`variant` filtering by hand, and makes `model_id` filtering match **primary model OR compatible**: `or_(Item.model_id == model_id, Item.id.in_(select(ItemCompatibleModel.item_id).where(ItemCompatibleModel.model_id == model_id)))`.
- `get_item` uses `select(Item).options(selectinload(Item.compatible_models)).where(...)`, never `db.get()` (which silently ignores loader options when serving from the identity map).

**`backend/src/catalog/dependencies.py` (new)**: `valid_item` — thin fetch-or-404 wrapper around `service.get_item`.

**`backend/src/catalog/router.py`**: `Category`/`Brand`/`Model` keep their `build_crud_router(...)` calls, untouched. Item's call replaced with a fully hand-written `APIRouter(prefix="/items", ...)` (5 routes, each delegating to `service.*`), mirroring the hybrid pattern already established by `cargo/router.py` and `payments/router.py`. Merged at the bottom via `router.include_router(...)` alongside the three generic sub-routers.

## Bug caught and fixed during implementation

The original plan's `list_items` route signature used `Annotated[PaginationParams, Query()]` alongside individual scalar filter params (`category_id`, `model_id`, `sku`, `variant`) — matching how `build_crud_router`'s generic engine and `payments/router.py` declare pagination. **This does not work once other plain scalar query params are added to the same endpoint**: confirmed empirically (not just via OpenAPI schema inspection) that FastAPI stops flattening `PaginationParams` into `page`/`page_size` query params and instead requires a single JSON `pagination` object, breaking every real request with a `422 Field required` on `pagination`. No existing hand-written endpoint in this codebase combines a `Query()`-annotated pagination model with extra filters (payments'/cargo's hand-written list endpoints take pagination alone, with no filters), so there was no precedent to catch this in advance.

**Fix**: `list_items` now takes `page`/`page_size` as plain `Annotated[int, Query(...)]` scalars (same shape as the other filter params) and reassembles them into a `PaginationParams` instance inside the route body before calling the service. Verified via real HTTP requests (see below) both before (422) and after (200) the fix.

## Not changed

`Category`/`Brand`/`Model` models, schemas, or routes; `Item.sku`'s immutability; the soft-delete behavior; any other domain.

## Verification performed

All against the running dev server (`uvicorn --reload`, port 8001) and dev Postgres, using the seeded admin login, via direct `curl` requests with a real bearer token:

1. `GET /catalog/items?page=1&page_size=5` and with `&category_id=...` — both returned `200` with correctly shaped items (previously `422` before the pagination-flattening fix above).
2. `PUT /catalog/items/{id}` with `compatible_model_ids: [4]` — item's `compatible_models`/`compatible_model_ids` updated and persisted (`GET` after confirms).
3. `GET /catalog/items?model_id=4` (iPhone 11 Pro) — returned **both** the item whose primary model is 4 and the item only tagged compatible with 4, confirming the OR-match filter.
4. `POST /catalog/items` with a nonexistent `compatible_model_ids: [999]` — clean `404` ("Compatible model id(s) not found or inactive: [999]"), not a raw DB integrity error.
5. `PUT` with `compatible_model_ids: []` — cleared the set. A separate `PUT` touching only `variant` (omitting `compatible_model_ids`) — left the existing compatibility set untouched, confirming the omitted-vs-explicit-empty-list distinction works as designed.
6. Full frontend round-trip (see `item-model-compatibility-frontend-plan.md`) exercised create/edit through the real UI on top of this API.

## Follow-ups (not part of this phase, flagged for later)

- No enforcement against tagging an Item's own primary `model_id` as also "compatible" with itself (harmless — the `list_items` OR-match is just redundant for that row — but not currently rejected). Add a validator if this needs to be a hard error later.
