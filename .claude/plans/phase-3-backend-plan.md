# Phase 3 Backend — Implementation Plan (executed)

## Context

`PLAN.md` defines Phase 3 ("Inventory / warehouse") and `.claude/specs/phase-3-backend.md` contains the full design for it — a new `inventory/` domain package that turns an allocated `PurchaseOrderLine` into a `StockLot` via a "Receive" action, plus a `StockMovement` audit trail for that receipt and for manual damage/loss/recount adjustments. Phase 0–2 (auth, ledger, generic CRUD, catalog, purchasing, cargo) were already built and confirmed unchanged from the spec's assumptions before implementation started — in particular, `PurchaseOrderLine.landed_cost_pkr` was already there and already populated by `cargo.service.create_shipment`; this phase never needed to touch `cargo` at all.

This plan executed the spec exactly as written — every file, table, and validation order matched §3–§7 with no design deviations — and reached the spec's "done when": for any model, you can see exactly how many units you hold, split by which lot they came in on and at what cost. **Status: complete and verified** — see the verification section below for the full walkthrough with real numbers. One genuine bug was found and fixed during verification (not present in the spec's own design, but in FastAPI's handling of it) — see the next section.

## Bug found and fixed during implementation: pagination flattening breaks when combined with filter params

`src/inventory/router.py`'s `list_stock_lots`/`list_stock_movements` are the first endpoints in this codebase to combine `PaginationParams` with additional plain query filters (`item_id`, `include_depleted`, `stock_lot_id`) — every existing list endpoint (`crud.py`'s generic factory, `purchasing.list_purchase_orders`, `cargo.list_shipments`) takes pagination alone. Following the spec's own router snippet verbatim (`Annotated[PaginationParams, Query()]` alongside the extra params) produced `{"detail":[{"type":"missing","loc":["query","pagination"],"msg":"Field required"}]}` on every call, including a bare `GET /inventory/stock-lots` with zero query params at all.

Isolated with a minimal two-route repro app (outside this codebase, run standalone with `uvicorn`) against the actual installed FastAPI (`0.141.1`): `Annotated[SomeBaseModel, Query()]` only flattens the model's fields into individual query parameters when it is the *only* query-affecting parameter on the endpoint. The moment a sibling plain parameter (`item_id: int | None = None`) is added to the same function signature, FastAPI stops flattening and instead expects a single literal `pagination` query value — which nothing can ever supply, so the endpoint is permanently broken regardless of what the caller sends. `Annotated[SomeBaseModel, Depends()]` (the older sub-dependency-class pattern) does not have this limitation and flattens correctly in every case tested, including alongside sibling params.

**Fix**: both `list_stock_lots` and `list_stock_movements` use `Annotated[PaginationParams, Depends()]` instead of `Query()`, with a comment explaining why (this file now looks different from `crud.py`/`purchasing`/`cargo`'s pagination parameter on purpose, not by accident). Scoped narrowly to these two functions — `src/pagination.py` and every other domain's existing `Query()`-based list endpoint were left untouched, since they never combine pagination with extra filters and aren't affected by this bug. Worth flagging for whoever builds Phase 4 or later phases: **any future list endpoint that needs a filter alongside pagination must use this `Depends()` form, not copy the `Query()` form from `crud.py`** — that's now a real trap in this specific FastAPI version, not a style choice.

## Build order (as executed)

### 1. `src/inventory/` (spec §3, §4, §5, §6)

`src/inventory/{__init__,constants,models,exceptions,utils,schemas,dependencies,service,router}.py` built following `cargo/`'s shape as the template, exactly per spec. `StockLot`/`StockMovement` have no `is_active` and no relationship attributes (spec §3.1 — neither response schema needs a nested collection, unlike `PurchaseOrder.lines`/`CargoShipment.allocations`). `StockLot.purchase_order_line_id` is a **unique** FK — the receipt marker itself (spec §2.1), so no column was added to `purchasing/models.py`. `service.receive_purchase_order_line` validates in order: line exists → `landed_cost_pkr is not None` → no existing lot for this line → insert `StockLot` (flush for id) → insert a `"receipt"` `StockMovement` → post one `LedgerEntry` (`account="Inventory"`, debit = `qty_received * landed_cost_pkr`, `reference_type="stock_lot"`) → flip `PurchaseOrder.status = "received"` if this was the PO's last unreceived line (single `outerjoin`+count query) → one `commit()` (`IntegrityError` → `ConflictException`). `service.create_adjustment` validates lot exists → `qty_delta != 0` → resulting `qty_remaining` inside `[0, qty_received]` → mutate + insert `"adjustment"` movement → commit. Mounted in `main.py` as `/inventory`.

### 2. `src/purchasing/constants.py` (spec §3.2)

Widened `PurchaseOrderStatus = Literal["draft", "allocated", "received"]`, comment updated to point at `inventory.service.receive_purchase_order_line` for the new transition. No other purchasing file touched — no migration needed for this by itself (`status` is already a plain `str` column).

### 3. `src/main.py` / `migrations/env.py`

`main.py` — added `inventory_router` import and `app.include_router(inventory_router, prefix="/inventory")`, same one-line-per-domain shape as every other router. `migrations/env.py` — added `from src.inventory.models import StockLot, StockMovement  # noqa: F401` to the model-imports block (Phase 2's plan flagged this exact step as easy to miss for autogenerate to see new tables; caught it up front this time instead of after a first failed autogenerate).

### 4. Migration

`alembic revision --autogenerate -m "add inventory"` produced a clean diff on the first try, matching the spec's expected diff exactly: `CREATE TABLE stock_lot` (with the unique index on `purchase_order_line_id`) and `CREATE TABLE stock_movement`, **no `ALTER TABLE` on any existing table** (confirming spec §2.1's design — receipt state genuinely needed no purchasing-side column). Correct `Numeric(10,2)`/`Numeric(12,2)` precisions, correct FK/index naming via the shared naming convention. Renamed to `migrations/versions/2026-08-08_add_inventory.py`; `alembic upgrade head` applied cleanly on top of Phase 0–2's schema.

### 5. Seed script

No changes — confirmed per spec §8 that `StockLot`/`StockMovement` are transactional records with nothing to seed, same reasoning already applied to `PurchaseOrder`/`CargoShipment`.

1. `ruff check` on every new/edited file (`src/inventory/*`, `src/purchasing/constants.py`, `src/main.py`, `migrations/env.py`) — clean. A full-backend `ruff check` afterward showed 27 pre-existing findings, all in files this phase never touched (old migration files' auto-generated `Union`/`Sequence` style, `crud.py`'s `Type[...]`, `parties/service.py`'s `date.today()`, `payments/router.py`'s import order) — same "pre-existing, not from this phase's edits" situation Phase 2's plan documented, not a regression.
2. `alembic upgrade head` — clean on top of Phase 0–2's schema.
3. `GET /openapi.json` — `/inventory/stock-lots` (GET list, POST, GET by id) and `/inventory/stock-movements` (GET list, POST) all present with correct `tags: ["inventory"]`, correct `PaginatedResponse_StockLotRead_`/`PaginatedResponse_StockMovementRead_` schemas registered.
4. **Pagination bug found and fixed** — see dedicated section above; retested clean after the fix.
5. **Happy-path receive, using real Phase 1/2 data** (PO 1, two lines, both already `landed_cost_pkr`-allocated from a Phase 2 cargo shipment):
   - `POST /inventory/stock-lots {purchase_order_line_id: 1, received_date: "2026-08-08"}` → `201`, `StockLotRead{qty_received: "10.00", qty_remaining: "10.00", landed_cost_pkr: "526.29", value_remaining_pkr: "5262.90"}`. PO 1 status checked immediately after: still `"allocated"` (line 2 not yet received) — confirms the "not last line" branch.
   - `POST /inventory/stock-lots {purchase_order_line_id: 2, ...}` → `201`, `qty_received: "3.00"`, `landed_cost_pkr: "358.41"`. PO 1 status re-checked: flipped to `"received"` — confirms the "last line" branch, both directions of spec §5.1 step 6 exercised.
   - `SELECT * FROM ledger_entry WHERE reference_type='stock_lot'` — exactly two rows, debits `5262.90` (`10 × 526.29`) and `1075.23` (`3 × 358.41`), both `credit=0`, both `account='Inventory'` — matches spec §2.4 exactly.
   - `SELECT * FROM stock_movement` — two `"receipt"` rows, `qty_delta` `10.00`/`3.00` matching each lot's `qty_received`, `reason` null.
6. **Negative cases on receive**, all clean 4xx, never 500: re-`POST`ing an already-received line → `409` (`"This purchase order line has already been received into a stock lot"`); a line whose `landed_cost_pkr` is still `NULL` (PO 2, still `"draft"`, never shipped) → `422` (`LineNotAllocated`); a nonexistent line id → `404` (`PurchaseOrderLineNotFound`); no bearer token → `401`.
7. **Adjustment flow**: valid `qty_delta=-2` on lot 1 (`reason="damaged in warehouse"`) → `201`, `qty_remaining` `10.00 → 8.00`, `value_remaining_pkr` recomputed to `4210.32`. Out-of-range checks: `qty_delta=-20` (would go to `-12.00`) → `422` with the exact bound in the message (`"outside [0, 10.00]"`); `qty_delta=+5` from `8.00` (would reach `13.00 > qty_received=10.00`) → `422`, confirming the upper bound (spec §5.2 step 3) actually fires, not just the lower one; `qty_delta=0` → `422`; nonexistent `stock_lot_id` → `404`.
8. **Fully depleting a lot** (`qty_delta=-3` on lot 2, `10.00`→ wait, `qty_received=3.00` → `0.00`) to exercise the `include_depleted` filter: default `GET /inventory/stock-lots?item_id=1` → only lot 1 (`total: 1`); `?include_depleted=true` → both lots (`total: 2`, lot 2 shown with `qty_remaining: "0.00"`, `value_remaining_pkr: "0.00"`). `item_id=3` filter (an item nothing has been received against yet) → `total: 0`, confirms the filter isn't a no-op.
9. `GET /inventory/stock-movements?stock_lot_id=1` → the 2 rows for that lot only (receipt + the `-2` adjustment); unfiltered `GET /inventory/stock-movements` → all 4 rows across both lots (`total: 4`).
10. `GET /inventory/stock-lots/{id}` for an existing lot → `200` with the same shape as the list; for a nonexistent id → `404`.
11. Auth: `GET /inventory/stock-movements` with no bearer token → `401`.
